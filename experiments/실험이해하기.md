# 실험 이해하기

3년 만에 다시 보는 사람을 위한 문서. 이 실험이 무엇을 재는지, 학습이 어떻게 돌아가는지,
왜 하루 넘게 걸리는지, 그 시간이 어디에 쓰이는지를 **이 저장소에서 직접 측정한 값**으로 설명한다.

---

## 1. 한 줄 요약

LA 고속도로 센서 207개의 과거 1시간 속도를 보고 **앞으로 1시간을 예측**하는 모델을 학습시킨다.
센서끼리 서로 영향을 주므로 "어느 센서가 어느 센서에 영향을 주는가"(그래프)를 같이 학습하는 것이
MTGNN 이고, 이 그래프를 **입력에 따라 매번 다르게** 만들자는 것이 석사논문의 기여다.

---

## 2. 데이터: 무엇을 보고 무엇을 맞히나

METR-LA 기준 (`data/metr-la.h5`):

| 항목 | 값 |
|---|---|
| 센서 수 (노드) | 207개 |
| 기간 | 2012-03-01 ~ 2012-06-27 |
| 측정 간격 | 5분 |
| 전체 시점 수 | 34,272 |

여기에 슬라이딩 윈도우를 씌운다. **12스텝(=1시간) 입력 → 12스텝(=1시간) 출력**:

```
시간축:  ... [t-11 ... t] [t+1 ... t+12] ...
          └── 입력 12개 ──┘└── 정답 12개 ──┘   (한 칸씩 밀며 반복)
```

그래서 샘플 하나의 모양은 `(12시점, 207센서, 2채널)` 이다.
2채널 = **속도 + 하루 중 시각**(time-in-day). 시각을 넣는 이유는 출퇴근 시간대 패턴 때문.

윈도우를 다 만들면 34,249개, 이를 7:1:2 로 나눈다:

| 분할 | 샘플 수 |
|---|---|
| train | 23,974 |
| val | 3,425 |
| test | 6,850 |

`horizon 3 / 6 / 12` 이라는 말은 각각 **15분 뒤 / 30분 뒤 / 60분 뒤** 예측 정확도를 뜻한다
(5분 간격이므로). 멀수록 어렵고, 논문 표도 이 세 개를 보고한다.

## 3. 모델이 하는 일

### 3.1 풀려는 문제

센서들은 서로 영향을 준다(상류가 막히면 하류도 막힌다). 그래프 신경망을 쓰려면 이 연결관계
(인접행렬 A)가 필요한데, **보통은 주어지지 않는다**. MTGNN 은 A 를 데이터로부터 같이 학습한다.

### 3.2 구성요소 세 가지

```
입력 (12, 207, 2)
   │
   ├─ graph_constructor ──> 인접행렬 A (207 x 207)
   │     노드 임베딩으로 A 를 만들고, 노드마다 상위 k=20 개만 남김
   │
   └─ [ TC -> GC ] x 3층 -> 출력층 -> 예측 (12, 207)
         TC(Temporal Convolution) : 시간축 패턴. 커널 1x2,1x3,1x6,1x7 을 동시에 쓰는 inception
         GC(Graph Convolution)    : A 를 따라 이웃 센서 정보를 섞음 (mix-hop)
```

- **TC** 는 시간 방향, **GC** 는 센서(공간) 방향을 담당한다. 이 둘을 번갈아 3번 쌓는다.
- TC 를 지날 때마다 시퀀스 길이가 6씩 줄어든다(커널 7, dilation 1). 그래서
  로그에 찍히는 `receptive field size is 19` 만큼 앞쪽을 0으로 패딩한 뒤 시작한다.
  길이 변화: **19 → 13 → 7 → 1**

### 3.3 석사논문의 기여

원본의 A 는 **입력과 무관한 고정 행렬**이다(노드 임베딩만으로 만듦). 논문은 여기에
`new_graph_constructor` 를 추가해 **입력 배치마다 다른 A**(모양 `(배치, 207, 207)`)를 만든다.

```
입력 ──┬─ TC 여러 층 ──> 시간 특징 ─┐
       │                            ├─> concat ─> 1x1 conv ─> sigmoid ─> A (배치, 207, 207)
       └─ GC 여러 층 ──> 공간 특징 ─┘
```

> 주의: 여기서 공간 특징을 뽑을 때 **원본의 고정 A 를 인접행렬로 사용**한다. 즉 동적 그래프는
> 고정 그래프를 완전히 대체하는 게 아니라 그 위에서 다듬는 구조다.

## 4. 학습 한 스텝에서 벌어지는 일

```
1) 배치 하나 꺼냄            (64샘플, 12시점, 207센서, 2채널)
2) 모델 통과(forward)        → 예측 (64, 12, 207)
3) 정답과 비교 → 손실(MAE)
4) 역전파(backward)          → 모든 파라미터의 기울기 계산
5) Adam 으로 파라미터 갱신
```

이걸 batch_size=64 로 하면 **한 epoch = 23,974 / 64 ≈ 375회** 반복이다.
(PEMS-BAY 는 36,465 / 64 ≈ 570회)

### 4.1 커리큘럼 러닝 — 가장 중요한 함정

`trainer.py` 를 보면 손실을 이렇게 계산한다:

```python
self.task_level = 1                      # 처음엔 1
if self.iter % self.step == 0 and self.task_level <= self.seq_out_len:
    self.task_level += 1                 # step_size1 = 2500 반복마다 +1
loss = self.loss(predict[:, :, :, :self.task_level], real[:, :, :, :self.task_level], 0.0)
```

**즉 처음에는 horizon 1(5분 뒤)만 학습하고, 2500 반복마다 학습 대상 horizon 을 하나씩 늘린다.**
쉬운 것부터 배우게 하는 기법인데, 실험 설계에 결정적인 영향을 준다:

| | METR-LA (375 iter/epoch) | PEMS-BAY (570 iter/epoch) |
|---|---|---|
| horizon 2 학습 시작 | 약 7 epoch | 약 4.4 epoch |
| horizon 12 까지 전부 학습 | **약 73 epoch** | **약 48 epoch** |

그래서 **epoch 을 함부로 줄이면 안 된다.** 30 epoch 만 돌리면 horizon 5 정도까지만 학습되고,
horizon 12 는 한 번도 학습되지 않은 채 평가된다. 논문이 100 epoch 을 쓴 이유가 이것이다.

실제로 이 저장소에서 1~2 epoch 만 돌려본 결과가 이를 그대로 보여준다:

| 설정 | horizon 1 MAE | horizon 3 MAE | horizon 12 MAE |
|---|---|---|---|
| `original` (1 epoch) | 2.5291 | 11.4984 | 11.5005 |
| `fixed_dyn` (2 epoch) | 2.4295 | 11.4984 | 11.5005 |

horizon 1 은 다르지만 **horizon 3 이상은 소수점 4자리까지 완전히 같다.** 두 모델이 학습되지
않은 구간에서 똑같이 "평균값"만 뱉고 있어서, 그 숫자는 모델이 아니라 **데이터의 성질**이다.
짧게 돌린 실행의 horizon 3/6/12 수치는 아무 의미가 없다는 뜻이다.

## 5. 왜 이렇게 오래 걸리나

### 5.1 실측값

M3 Pro(11코어/18GB), `--device mps`, METR-LA:

| 설정 | 파라미터 수 | 1 epoch 시간 | 1회 반복 |
|---|---|---|---|
| `original` (원본 MTGNN) | 405,452 | **67.3초** | 0.18초 |
| `fixed_dyn` (동적 그래프) | 764,219 | **194.3초** | 0.52초 |

**동적 그래프를 켜면 2.9배 느려진다.** 100 epoch 기준으로 원본 1.9시간 vs 동적 5.4시간.

전체 실험(5설정 × 100 epoch × 1 run)이 약 29시간인 이유:

```
설정 5개 × 100 epoch × (67 ~ 194초) ≈ 25 ~ 30시간
```

### 5.2 시간이 어디에 쓰이나

**핵심은 그래프 합성곱의 N² 연산이다.** 인접행렬이 207×207 이라 모든 센서 쌍을 다 계산한다.

한 번의 forward 에서 그래프 합성곱만 대략:

```
배치 64 × 채널 32 × (207 × 207) × 시퀀스길이 × (층당 4회) × 3층
= 약 7.4 G MAC   (층별 시퀀스 길이 13, 7, 1 반영)
```

역전파까지 하면 반복 1회에 대략 그 3배. TC(시간 합성곱)는 이보다 한참 작다.
**노드 수가 늘면 제곱으로 늘어난다** — PEMS-BAY(325노드)가 METR-LA(207노드)보다
훨씬 느린 이유다. (325/207)² ≈ 2.5배.

### 5.3 그런데 왜 FLOP 에 비해 유난히 느린가

M3 Pro GPU 의 이론 성능은 수 TFLOPS 인데, 위 계산으로는 반복 1회가 0.18초씩 걸릴 이유가 없다.
실제 병목은 **연산량이 아니라 작은 연산의 개수**다:

- TC 한 층에 inception 커널이 4개(1x2, 1x3, 1x6, 1x7) × filter/gate 2벌 = **8개의 작은 conv**
- GC 한 층에 mixprop 2개 × (전파 2회 + mlp) = **6개의 작은 연산**
- 여기에 residual conv, skip conv, LayerNorm...
- 3층이므로 forward 한 번에 GPU 커널이 **수십~100개 남짓**, 역전파까지 하면 그 3배

즉 **큰 행렬 곱 하나가 아니라 자잘한 연산 수백 개**를 매 반복마다 던진다. 이런 형태는
GPU 연산기보다 **커널 실행 오버헤드와 메모리 대역폭**에 좌우된다. 게다가 MPS(Apple GPU)
백엔드는 CUDA 만큼 최적화되어 있지 않고, 일부 연산은 CPU 로 떨어지기도 한다.

동적 버전이 2.9배 느린 것도 같은 이유다. `new_graph_constructor` 가 사실상 **또 하나의
3층 TC+GC 스택**이라 연산 개수가 거의 두 배가 되고, 게다가 인접행렬이 배치마다 달라져
(`nconv2`) 배치 전체가 공유하던 행렬 곱을 **샘플별로** 하게 된다.

### 5.4 메모리

파라미터는 76만 개(약 3MB)로 아주 작다. 메모리를 먹는 건 **중간 활성값**이다:

```
배치 64 × 채널 32 × 노드 207 × 시퀀스 19 ≈ 800만 개 원소 ≈ 32MB   (텐서 하나당)
```

이런 텐서가 층마다 여러 개, 게다가 역전파를 위해 forward 결과를 전부 붙들고 있어야 한다.
동적 버전은 여기에 `(64, 207, 207)` 인접행렬(약 11MB)이 배치마다 추가된다.
18GB 램에서는 문제없지만, 배치를 키우거나 노드가 많아지면 여기서 먼저 막힌다.

### 5.5 죽은 파라미터

측정하다 발견한 것:

| 구분 | 파라미터 수 |
|---|---|
| baseline 상당 | 405,452 (원본과 정확히 일치) |
| `new_gc` 추가분 | 358,767 |
| ┗ 그중 **한 번도 쓰이지 않는** `self.norm` | **278,208 (추가분의 77.5%)** |
| ┗ 실제로 동작하는 부분 | 80,559 |

`new_graph_constructor.__init__` 이 층마다 `LayerNorm` 을 만들어 두지만 `forward` 는
그걸 전혀 호출하지 않는다(AST 로 확인). 옵티마이저에는 들어가 있으므로 **메모리와 옵티마이저
상태만 차지하고 학습에는 기여하지 않는다.** 동적 모델 전체 파라미터의 36%가 여기다.

## 6. 그래서 이 실험으로 무엇을 아나

코드 리뷰에서 발견한 문제가 출발점이다. 정적 그래프를 만들 때
`alpha` 값이 원본은 3인데 이 코드는 0.05 로 들어가 있었다. 이 값은 **baseline 과 Dynamic
양쪽 모두**에 영향을 주므로, 논문 표의 "MTGNN vs Dynamic MTGNN" 비교 자체가 흔들린다.

그래서 5가지 설정을 같은 조건으로 돌려 비교한다:

| 확인 순서 | 비교 | 무엇을 알 수 있나 |
|---|---|---|
| 1 | `original` vs 원본 논문 수치 | 내 실행 환경이 정상인가 (여기가 어긋나면 나머지 무의미) |
| 2 | `fixed_base` vs `original` | 기여 코드의 baseline 경로가 원본에 충실한가 |
| 3 | `thesis_base` vs `fixed_base` | alpha 버그가 baseline 을 얼마나 망가뜨렸나 |
| 4 | `fixed_dyn` vs `fixed_base` | **올바른 조건에서 기여의 순수 효과** |

4번이 이 재실험의 결론이다. 논문은 "성능을 유지하면서 동적 그래프를 만든다"고 주장하는데,
그 주장이 **제대로 된 baseline 과 비교해도 살아남는지**를 본다.

참고로 파라미터 수 확인에서 이미 2번의 절반은 검증됐다: 기여 코드에서 동적 그래프를 끄면
파라미터가 405,452개로 **원본과 정확히 일치**한다. 구조적으로 같은 모델이라는 뜻이다.

## 7. 결과 읽는 법

```bash
./venv/bin/python experiments/summarize.py --dataset METR-LA
```

- **MAE**: 평균 절대 오차. 예측이 실제 속도(mph)에서 평균 몇이나 빗나갔나. 낮을수록 좋다.
- **RMSE**: 제곱평균제곱근 오차. 큰 오차에 더 민감하다. 낮을수록 좋다.
- **MAPE**: 평균 절대 백분율 오차. 낮을수록 좋다.
- **Horizon 3 / 6 / 12**: 15분 / 30분 / 60분 뒤 예측.

METR-LA 에서 MAE 가 대략 2.6~3.5 정도면 논문 수준이다. **10을 넘으면 학습이 안 된 것**이므로
epoch 수나 커리큘럼 러닝(4.1절)을 의심해야 한다.

## 8. 자주 헷갈리는 것

**Q. train loss 는 2.6인데 valid loss 가 10.6이다. 과적합인가?**
아니다. 커리큘럼 러닝 때문이다. train loss 는 그 시점까지 학습 대상인 horizon 만(초반엔 1개)
계산하고, valid loss 는 **항상 12개 horizon 전부**로 계산한다. 애초에 다른 것을 재고 있다.
학습이 진행돼 task_level 이 12에 도달하면 격차가 줄어든다.

**Q. 짧게 돌렸더니 두 모델 결과가 똑같다. 코드가 잘못됐나?**
아니다. 4.1절 참고. 학습되지 않은 horizon 에서 두 모델 모두 상수(평균)를 뱉기 때문이다.

**Q. epoch 을 줄여서 빨리 보면 안 되나?**
horizon 1 만 볼 거라면 가능하다. 하지만 논문 표(horizon 3/6/12)와 비교하려면
METR-LA 는 최소 73 epoch 이 필요하다. 줄이려면 차라리 `--runs 1` 로 반복 횟수를 줄이는 게 낫다.

**Q. `Results for 10 runs` 라고 찍히는데 나는 1 run 만 돌렸다.**
원본 코드의 출력 문자열이 10으로 하드코딩되어 있다. 실제 반복 수는 `--runs` 값이 맞다.

**Q. MAPE 가 0.3135 로 나온다. 31%인가?**
그렇다. 코드는 분수로 저장하고 요약 스크립트가 100을 곱해 %로 보여준다.

python3 experiments/setup.py                                   # 최초 1회
./venv/bin/python experiments/run.py --list                    # 설정 확인

오래 걸리는 실행은 로그가 `experiments/results/<데이터셋>/<설정>/train.log` 에 실시간으로
쌓이므로, 다른 터미널에서 `tail -f` 로 지켜보면 된다.
